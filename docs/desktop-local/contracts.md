# 本地模式契约

这份文档是桌面端与本地后端之间的**事实约定**。代码里用 `contracts.md §N` 引用的地方，指的就是下面编号对应的小节：改这里的约定等于改契约，两侧要同时改。

## 一句话概括

Chiron 是**单机、单用户的本地 agent**。运行形态是三个进程加一个数据栈：Electron 外壳负责拉起数据栈与后端，Go 网关是**唯一业务入口**，Python 引擎承担对话/知识库/技能等重业务。

```
Electron 主进程
  ├─ spawn → chiron-launcher（数据栈引导器，无端口）
  │             └─ embedded PostgreSQL + bundled Redis
  ├─ spawn → chiron.exe（Go 网关，唯一业务入口）
  └─ spawn → python-engine（FastAPI，重业务）
```

## §1 运行模式与设备级设置

**只有一个运行模式：`local`。** 云端模式已废除。`MODES` 枚举仍保留 `cloud`，只是为了让历史 `config.json` 能被读取而不抛错；`resolveMode()` 恒返回 `local`，任何残留的 `mode: "cloud"` 与环境变量都不再生效。

`config.json` 是**设备级设置的真相**，位于数据目录根下。渲染进程的 `localStorage` 只是镜像，用于首屏快速读取，不作为判据。

设备级设置包含：运行模式、本地数据目录与上次启动时间、界面偏好（语言/主题）、以及老版本迁移状态。

**切换模式不再是一个动作。** 既然只有本地一种形态，就不存在"切换"这个操作，界面上也没有入口。

## §2 preload 契约

渲染进程**只能**通过 `window.chironDesktop` 访问主进程能力，不暴露 `require`，也不暴露任意 `ipcRenderer` 通道。

暴露面分两类：

- **只读信息**：平台、是否桌面壳、服务地址、运行模式、设备设置快照、当前 OS 账户
- **明确动作**：重启、改服务地址、读写设备 token

每条能力都必须能在 Web 端优雅降级：`window.chironDesktop` 不存在时，判据返回 `false`、动作返回 `false` 或空值，**不允许抛错**把设置页打挂。

新增成员时同步三处：`preload.cjs` 的暴露对象、`src/stores/device.ts` 的可选接口、以及 `main.cjs` 的 `ipcMain.handle`。三者漏一处**不会**在类型检查里报错（接口成员是可选的），只会在运行时静默失效。

## §3 组件

本地组件是**可选能力包**，当前有两个：

| 组件 | 作用 |
|---|---|
| `pageindex` | 文档索引服务，供知识库页面级检索 |
| `langextract` | 结构化抽取 |

组件的安装源**由用户提供**，本仓库不内置任何下载地址。`CHIRON_COMPONENT_BASE_URL` 指向一个本地目录（`<源>/<name>/manifest.json`）或一个 HTTP 基址。**未配置时安装直接失败**并报 `component_source_unconfigured`，绝不静默成功。

安装产物只落在 `<data-dir>/components/<name>/<version>`，全程在 `.tmp` 临时目录完成、校验通过后才迁移过去，失败不留残骸。

**安全口径**：路径穿越（`..`、绝对路径、盘符、符号链接）在解压前逐条目拦下；每个待安装文件都必须有 sha256 校验值。这两条不依赖 `extractall` 的默认行为，因为它的默认行为随 Python 版本变过。

组件的 CLI 入口是引导器的子命令，不是 HTTP 端点 —— 引导器刻意没有端口，加一条 HTTP 面会与"打印一行就绪 JSON、靠 stdin EOF 存活"的生命周期冲突。

### §3.1 环境变量

- `CHIRON_*` —— **契约名**，跨端共享的正式名称
- `CHIRON_LOCAL_*` —— 当前实现使用的具体名

共享常量集中在 `frontend-vue/electron/shared.cjs`，两侧都从那里读，读不到才用同一个兜底字面量。这样把常量搬家时两边同时生效，不会单边漂移。

## §4 本地身份

本地模式**没有注册、没有登录页**。身份来自 OS 账户：

> 一个 Windows 用户 = 一个应用用户。

会话由网关按请求来源**免口令签发**：`POST /v1/auth/session`，仅当 `LOCAL_BOOTSTRAP` 开启时注册该路由。请求必须是 **loopback 来源**（只看 `RemoteAddr`，不看任何转发头 —— 转发头是客户端可自填的，拿它判"是不是本机"等于把闸门交给请求方）。

引导账号固定为 `owner@chiron.local`、角色 `owner`。用固定值而非随机值有两个理由：一是唯一索引天然幂等，每次重启命中同一行，不会积累出一堆本地账号；二是局域网设备登录时得知道该输哪个邮箱。该账号的口令**不由系统生成**，必须由本机用户自己在「设置 → 账户」里首设。

`POST /v1/auth/register` 在桌面端被**无条件关闭**：本地栈强制注入 `DISABLE_REGISTRATION=1`，且不保留"调用方显式传值就能打开"的口径。理由是本地模式不存在"新账号"这个概念，留着这条端点等于给本机留一条凭空造出第二个账号的路。

> 注意区分作用范围：这个开关只在**桌面壳**注入。源码态 `python run.py start` 不注入，开发环境仍可注册首个管理员账号。

## §5 数据目录与隔离

数据目录固定为 `%APPDATA%\gh_Athenavi_chiron`。不用包名 `frontend-vue`：那是安装后默认会得到的目录名，用户既认不出也不敢删。

隔离靠**两层**，缺一层都不够：

1. **路径层**：`CHIRON_DESKTOP_USER_DATA` 的覆盖值必须落在当前用户的 `appData` 之内，越界即回落到默认根。判据是路径包含关系，不是在字符串上比前缀。
2. **权限层**：启动时对数据目录根跑一次 `icacls`，移除继承并只授予当前账户完全控制。`local/` 子树后续创建时会继承根的权限，所以不必逐层递归。

`chmod 0700` 在 Windows 上**被忽略**，不能作为隔离依据。权限操作失败只记日志、不阻断启动——组策略或网络盘都可能让它失败，那不该让应用起不来。

Electron 的 session 分区是 `persist:chiron-local`。它只隔离渲染进程的存储，**不保护数据目录里的文件**，两者是不同层的机制。

## §8 推理代理

组件与引擎的模型调用统一经过主进程的推理代理，**不直连上游**。这样凭据只在主进程内存里，渲染进程与组件进程都拿不到。

硬约束：

- 代理只接受 loopback 连接
- 上游地址与密钥由主进程注入，不接受子进程自报
- 任何"跳过代理直连"的实现都视为破坏契约

## §9 用量

本地只做**用量统计**，不做计费：没有套餐、没有额度、没有发票。

推理代理在转发时记录 token 用量与会话归属，作为对账与后续自动计费的输入。这条链路**只记账、不扣费**。

## 启动失败时的行为

本地后端拉起失败时，界面**不能白屏**。分流规则：

- 数据栈没起来 → 错误页，写清原因，提供重试
- 数据栈已起但网关/引擎失败 → 错误页，可重试或退出
- 安装未完成 → 进度窗口，装完自动进主界面

失败一律**非零退出**并记日志。装作起来了只会把错误推迟到更难看懂的地方。

## Windows Hello 二次确认

身份来自 OS 账户，意味着"能坐到这台机器前的人自动就是账户主人"。共用工作站上，登录 Windows 的人走开而屏幕未锁时，回来的是另一个人。

所以启动后加一道 `UserConsentVerifier`（PIN / 指纹 / 人脸）。它验证不了"是谁"，但能证明"还是同一个已通过 OS 登录的人在场"。

| 情况 | 行为 |
|---|---|
| 设备可用且验证通过 | 放行 |
| 设备可用但用户取消 / 重试耗尽 | 退出应用 |
| 设备不可用（无 TPM、无生物识别） | 跳过确认 |
| 探测或调用本身失败 | 跳过确认并记日志 |

**为什么设备不可用要跳过**：这道确认是加固，不是访问控制前提。让它拦住启动，等于让一部分机器永远进不去应用。

这道确认挡不住"账户本人主动点了通过"，它防的是**旁人**。
